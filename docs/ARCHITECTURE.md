## 採用する接続構成

```text
Office UI（Research Lab / 秘書を含む。画面詳細は要確認）
    ↕ 操作・状態表示
CXランタイム：app-serverの主クライアント（B）
    ↕ stdio または認証付きWebSocket（採用方式未決）
Codex app-server
    ↕ モデル・ツール・外部サービス（権限と承認の境界）
```

検証01ではstdioで初期化・一覧・設定読み取り、02ではNodeのHTTP Upgrade経由でBearer認証付きWebSocket接続を確認した。ブラウザからの直接接続は確認していない。ブラウザ向けの仲介層、認証情報の保持場所、Origin検査は別途検討する。複数接続成功は、複数クライアントの安全な同時操作を保証しない。

PowerShellなどの外部端末とOfficeが同じ作業・会話へ参加する体験は作者確認済み。完全な画面同期は確定要件ではない。app-serverとremote TUIの組み合わせ、およびPowerShellとOfficeによる同一Thread操作は実現方法の検証事項とする。

### B：主接続（作者採用済み）

Office UIはCXランタイムを通じて操作する。CXランタイムが以下を管理する。

- Threadの生成・選択・状態管理、TurnとItemのイベント取得。
- エージェントの活動状態、入力・追加指示、承認・拒否。
- セッションと成果の永続化。
- Research Labと秘書のジョブ管理。

管理責務の採用であり、保存形式、Codex側保存との役割分担、ジョブの実行方式、通信方式や配布方式まで確定したものではない。

### A：PowerShell連携の補助方式（作者採用済み）

CXが管理するremote TUIを対象に、必要に応じて通信を仲介し、PowerShellとOfficeが同じ作業に関与できる体験を目指す。TUIとOfficeの入力・承認の競合を管理し、既存のPowerShell操作感をできるだけ維持する。仲介の配置や競合解消の具体的な方式は未確定。管理外のCodexセッションを無条件に後付け観測できるとは扱わない。

### C：独立接続とresumeによる共同観測（保留）

復元時の副作用と購読成立の問題が解消するまで主経路に採用しない。thread/readは購読成立の証拠にならず、resumeも副作用のない観測専用操作とは扱わない。検証06では新規未実行Threadのresumeがrollout不在で失敗し、検証08では自動キュー配送の可能性を確認して実測前に停止した。詳細な根拠は[VALIDATION_PLAN](VALIDATION_PLAN.md)を参照。

## Thread / Turn / Itemとイベント管理

設計上の仮置きとして、Threadを会話の単位、Turnを依頼から処理終了までの単位、Itemをメッセージ・ツール作業等の表示単位として整理する。正確な関係、型、ID、通知名、終了状態は未確認であり、実装契約にはしない。

- 接続ごとの初期化とリクエストIDの管理を分ける。検証02ではA・Bが同じ数値IDを使い各接続で応答を受けた。
- Thread／Turn／Itemの識別子と観測したイベントを関連付け、根拠付きでUI状態へ変換する案。
- 実行中、承認待ち、完了、失敗、切断による不明を混同しない。重複・遅延・順序逆転を扱う方式は検証後に決める。
- 再接続時に一覧・履歴等で状態を再取得できるかを検証する。通知再送、取りこぼし回復、サブエージェントとThreadの対応は未検証。

## 承認と責務の境界

開発作業の承認はAGENTS.mdに従う。製品ではOfficeからセッション選択・切替・観察・入力・承認・拒否を行えることが作者確認済み。秘書は編集・追加可能なSkillsに従って提案を準備し、利用者が対話で修正した後、最終実行前に修正後の内容を提示して明示承認を得る。未承認のメール送信・予定変更等を実行しない（S7）。

未確定なのは要求ID、回答先、拒否・期限切れ・再接続後の扱い、承認・拒否の配送と競合、複数クライアントの二重回答対策である。UIの表示解除を承認回答として扱わない設計を候補とする。製品方針の合意は、今回の開発作業や外部操作の実行許可ではない。

## フェーズ1の具体化（2026-11-15、S10）

作者のフェーズ1開始指示により、上記の「文書更新のみ」という当時の作業制約は今回の範囲で更新された。製品のB主接続・A補助・C保留は維持する。

```text
Office UI (新規SVG / ES modules)
    → loopback HTTP / Cookie / Host・Origin検査 / 固定API
CX Runtime (JSON-RPC / Thread状態 / 承認ロック / メタデータ保存)
    → 所有子プロセスのstdio
Codex app-server 0.169.0
```

フェーズ1ではNode.js標準機能＋ブラウザES modulesを採用。実行時依存とビルド工程を増やさず、プロトコル接続factoryと状態投影を分離した。Aの仲介transport追加余地を残すが未実装。製品画面はメソッドを自由送信できず、CX作成Threadの固定操作だけを扱う。

新規Threadは作成接続で観測し、Thread/Turn/Item IDを分離して投影。終了通知だけをTurn終了の根拠とし、Item完了をTurn完了にしない。遅延startは既知の終端状態を戻さない。deltaの完全な重複識別は保証せず、完成Item本文を正とする。未知型はunknown。

再接続時は認証・設定確認と既知IDへのreadによる照合のみ。resume、キュー投入、入力再送はない。旧Threadは購読未復旧・参照のみとして管理する。新規作成と再開を混同しない。重要な永続化対象はThread ID、選択、直近イベントメタデータ。本文はCX診断保存せず、履歴本文はCodex側に委ねる。

承認は要求ID・Thread/Turn/Itemで関連付け、送信前に状態をロックする。回答送信・serverRequest/resolved・切断による不明を区別。判断材料がない場合のacceptと追加権限/ネットワーク承認は無効。未知の要求を自動承認しない。

実機接続・モック検証・未実測の詳細は[PHASE1](PHASE1.md)を参照。実行時モデル送信は既定で無効。実モデルの検証には作者による対象・回数・影響の承認が必要。

### 認証境界の修正（2026-11-15）

作者の安全対策実装指示により、上記の再接続時read照合を廃止。認証/接続世代を照合し、変更・不明時は共通ゲートを閉じ、旧Threadと表示内容を隔離する。保存IDは現在の本人へ帰属させない。明示再接続後も新規Threadだけで再開し、resumeを行わない。送信・承認前のaccount/readは変更検知の補助であり、安定した本人一致や別CLIでの変更の即時検知を保証しない。詳細は[実装記録](AUTH_BOUNDARY_IMPLEMENTATION.md)。B主接続・A補助・C保留は変更しない。
